# 冷库网关：采集进程热换版 + 单路暂停收数，记录仪 TCP 长连接不断

冷库温度记录仪通过 **一条 TCP 长连接** 持续上发逐行 JSON 读数。网关侧的
采集进程需要换版（v1 → v2），要求：

- 记录仪只连接一次，换版期间 TCP 连接不中断、不重连；
- 旧进程处理完手头已收到的完整读数后，把连接交给新进程；
- 已发出但尚未处理的读数沿原连接按发送顺序继续收，每条只确认一次；
- 新版启动失败时自动回退，旧进程继续收数；
- FastAPI 操作页展示每笔确认的读数编号与处理进程版本。

值班员还可以 **暂停任一路连接的收数**（例如暂缓一路历史补报），让同网关的
其他记录仪继续上报：

- 操作页可同时启动 **两台** 模拟记录仪（各自只连一次），并选中任一已建立
  的连接暂停 / 恢复收数；
- 暂停生效后网关停止读取这条 TCP 连接，该路不再新增确认，其他连接照常；
- 换版成功或新版启动失败后暂停仍然有效，原连接与已读到的半行都保留；
- 恢复后沿原连接拼完半行、按发送顺序继续收，每笔仍只确认一次；
- 页面显示各路 **实际生效** 的状态与确认编号；交接中暂不能生效的操作
  （暂停/恢复）返回 409 并提示重试。

## 工作原理

```
                ┌──────────────────── gateway 容器 / 单 supervisor 进程 ───────────────────┐
  记录仪(客户端) │  TCP:9000 ── accept ──┐                                                  │
  只 connect 一次 │                        │ SCM_RIGHTS 传连接 fd（SOCK_SEQPACKET 控制通道）  │
  逐行 JSON 连发  │                        ▼                                                  │
                │              ┌──────────────────────┐        ┌──────────────────────┐     │
                │              │ 采集进程 v1（子进程）  │ 换版   │ 采集进程 v2（子进程）  │     │
                │              │ 持有记录仪 TCP fd      │ ─────▶ │ 接手同一个 TCP fd      │     │
                │              └──────────────────────┘        └──────────────────────┘     │
                │                        ▲  启动失败：v2 退出，v1 继续收数（自动回退）           │
                │              FastAPI 操作页 :8000（启动记录仪 / 换版 / 模拟失败 / 校验）     │
                └──────────────────────────────────────────────────────────────────────────┘
```

关键机制：

1. **监听 socket 归 supervisor 所有**，采集进程是独立子进程（独立版本号、独立 pid），
   自身不 accept 连接。supervisor accept 后通过 Unix 域套接字 + `SCM_RIGHTS`
   把 TCP 连接 fd 发给当前采集进程。
2. **换版即 fd 交接**，不是断连重连。内核里同一个 `struct file`（同一四元组、
   同一接收缓冲区）被复制到新进程，记录仪完全无感知。
3. 控制通道选用 **`SOCK_SEQPACKET`**：既面向连接、可靠，又保留消息边界，
   保证一次 `recvmsg` 同时取到整帧和附属 fd（STREAM 上先读长度头会吞掉
   SCM_RIGHTS 辅助数据，这是本项目实现中实测踩过的坑）。
4. **半行不丢不重**：旧进程换版时先把缓冲区与内核中已到达的**完整行**全部处理，
   剩余的不完整半行（leftover）随 fd 一起交给新进程；新进程先拼完半行再继续读。
5. **逐条确认、仅一次**：每个读数 id 的确认事件按连接记录，服务端实时检测重复确认；
   `/api/verify` 独立校验编号 1..N 连续、无重复、版本分界为干净的前缀/后缀。
6. **启动失败回退**：换版先拉起新版本并等待 `ready`；失败标记文件存在时新版本
   启动即失败，supervisor 不发起交接，旧进程与原连接原封不动继续工作。
7. **单路暂停/恢复**：supervisor 持有暂停集合（`paused_peers`），通过控制通道
   命令采集进程把该连接移出读循环（停止读取这条 TCP 连接，内核缓冲区自然积压，
   对端发送窗口打满后自然节流）。暂停状态随换版交接帧一起交给新进程
   （supervisor 在中继 `new_conn` 帧时按暂停集合打标），因此换版成功、
   新版启动失败回退后暂停都仍然有效；已读到的半行留在该连接的缓冲区里随
   fd 一起走。恢复时采集进程先把缓冲区里保存的半行拼完、处理完已缓冲的
   完整行，再回到正常读循环。暂停中的连接在交接时**不再 drain**（否则会产生
   新确认，违背“暂停即不再新增确认”）。

读数行格式（`\n` 结尾的 JSON）：

```json
{"id": 7, "sensor": "freezer-1", "temp_c": -18.4, "ts": 1731000000.123}
```

## 用 Docker Compose 启动

```bash
cd gateway
docker compose up --build
# 操作页：  http://localhost:8000/
# 记录仪 TCP： localhost:9000
```

页面操作（也全部有对应 REST API）：

1. **① 模拟记录仪**：A/B 两个槽位可同时各启动一台（传感器 freezer-1 /
   freezer-2），各自只建立一次 TCP 连接。可设置总数/间隔/暂停点制造换版窗口。
2. **② 连接暂停/恢复**：表格列出每条已建立连接的实际生效状态（收数中 /
   已暂停 / 生效中… / 已关闭）、已确认笔数、最后确认编号、缓冲区半行字节数；
   点“暂停收数”暂缓该路（如历史补报），点“恢复收数”继续。交接进行中按钮
   禁用，直接调 API 会收到 409 + `retry:true`，提示稍后重试。
3. **③ 换版**：输入新版本号 `v2`，点“执行换版 / 交接”。勾选“模拟新版启动
   失败”可演练回退；也可用“放置失败标记”按钮手动制造失败。
4. **⑤ 逐笔确认** 表格实时显示每笔读数编号、处理进程版本、温度、连接、确认序号。
5. **⑥ 校验结果** 显示编号连续性、唯一性、各版本处理的编号区间，以及重复确认计数。

也可以用 compose 里的独立记录仪容器（同一镜像，recorder profile）：

```bash
docker compose --profile recorder run --rm recorder \
  python -m app.recorder --host gateway --port 9000 --count 60 --gap-at 20
```

## REST API 摘要

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET  | `/api/status` | 当前版本、各代进程状态、**各路连接实际生效状态**、记录仪槽位、失败标记、重复确认 |
| GET  | `/api/events?cursor=N` | 增量事件流（确认、暂停/恢复、换版、日志…） |
| GET  | `/api/verify` | 每连接编号连续性/唯一性/版本分界的独立校验 |
| POST | `/api/upgrade` | `{"new_version":"v2","simulate_fail":false}` |
| POST | `/api/connections/pause` | `{"peer":"127.0.0.1:5001"}` 暂停该连接收数；交接中返回 409+`retry:true` |
| POST | `/api/connections/resume` | `{"peer":"127.0.0.1:5001"}` 恢复该连接收数 |
| POST | `/api/recorder/start` | `{"count":60,"interval":0.2,"gap_at":20,"gap_seconds":5,"recorder_id":"r1"}`；可同时 r1/r2 两台 |
| POST | `/api/recorder/stop` | `{}` 全部停止，或 `{"recorder_id":"r1"}` 停一台 |
| POST | `/api/fail-marker` | `{"present":true}` 手动放置/清除启动失败标记 |
| POST | `/api/events/reset` | 清空事件与确认记录 |

## 设计取舍与边界

- 采集进程与 supervisor 放在**同一容器**内：fd 交接依赖同一内核网络命名空间
  与 Unix 套接字，跨容器需要共享 pid/network namespace，复杂度更高且无收益。
- 换版进行中到达的新 TCP 连接会在监听 backlog 中短暂等待，继任者就绪后再投递，
  不会交给即将退出的旧进程。
- 暂停/恢复与换版共用同一条有序控制通道：换版**之前**下发的暂停一定先于交接
  生效；交接**进行中**的暂停/恢复请求被拒绝（409 + `retry:true`），值班员稍后
  重试即可，不会半途中断交接。
- 暂停以连接四元组（`ip:port`）标识；暂停中的连接若被对端关闭，网关不读它，
  要到恢复收数（或交接后恢复）时才发现 EOF——期间该连接在页面上仍显示“已暂停”。
- 若**活动采集进程异常崩溃**（非换版场景），其持有的连接 fd 随进程释放，
  记录仪会收到 EOF；supervisor 会自动重启同版本进程，并把连接表中的对应连接
  标记为已关闭、清掉其暂停状态。换版路径本身不会断连。
- 失败标记是演示“新版启动失败”的模拟手段（文件存在即启动失败），真实系统中
  对应健康检查/版本初始化失败。
